## Executive summary

If the SIEM (`../../../01-siem-log-analysis/`) is "the brain" that sees and correlates, Wazuh is "the muscles": it does not just detect, it acts. This file documents the two capabilities that turn Wazuh from a simple sensor into an active defense system (XDR - Extended Detection and Response): threat detection on the endpoint and automated response.

**File Integrity Monitoring (FIM)**, via the Syscheck module, watches critical files and directories and alerts on every unauthorized modification: it is the direct countermeasure to the persistence and tampering seen in `07-post-exploitation` (an attacker who modifies `/etc/passwd`, adds an SSH key or alters a system binary is detected). **Rootcheck** searches for rootkits and known anomalies. Finding DEF-003 documents this endpoint detection capability.

**Active Response** is the qualitative leap: Wazuh can automatically execute a response script when a rule triggers - typically blocking an attacker's IP at the firewall level. Finding DEF-004 documents this automated response, which reduces the time between detection and containment to seconds, without human intervention.

## File integrity monitoring and threat detection

**Finding ID:** `DEF-003` | **Severity:** `High` (detection of tampering with critical files, persistence and rootkits on the endpoint)

### Operational context

Wazuh's Syscheck module computes and stores the hashes (checksums), permissions and attributes of the monitored files; at regular intervals (or in real time with `<realtime>`) it recomputes and compares, generating an alert on every discrepancy. It is the direct countermeasure to persistence techniques: modifications to `/etc/passwd`, `/etc/sudoers`, `authorized_keys`, Windows Run registry keys, or system binaries.

### PoC - FIM configuration (syscheck)

```XML
<!-- /var/ossec/etc/ossec.conf on the agent (or via group from the Manager) -->
<syscheck>
  <directories realtime="yes" check_all="yes">/etc,/usr/bin,/usr/sbin</directories>
  <directories realtime="yes" check_all="yes">/root/.ssh</directories>
  <!-- alert on modifications to critical authentication files -->
</syscheck>
```

### PoC - detection of an unauthorized modification

```Bash
# [Attack simulation] addition of a backdoor SSH key
echo "ssh-rsa AAAA...attacker" >> /root/.ssh/authorized_keys
```

```
# Alert generated by the Manager (rule 550: Integrity checksum changed)
** Alert 1699887766.12345: - ossec,syscheck,
Rule: 550 (level 7) -> 'Integrity checksum changed.'
File '/root/.ssh/authorized_keys' modified          <-- persistence detected (DEF-003)
Attributes: size, md5, sha256 changed
```

```Bash
# Rootcheck: scan for rootkits and known anomalies
/var/ossec/bin/wazuh-control restart
# rootcheck alerts appear in the Dashboard under rule.groups:rootcheck
```

### Tuning and defensive operations

- **Targeted selection:** monitor in `realtime` only the critical paths (authentication, binaries, cron, keys); FIM on large and volatile directories generates noise
- **Ignore list:** exclude legitimately volatile files (logs, cache, temp) to reduce false positives
- **Baseline:** establish a clean baseline right after hardening (`../../../04-hardening-scripts/`), so every subsequent deviation is significant
- **Correlation:** forward the FIM alerts to the SIEM to correlate them with other events (a modification to `authorized_keys` + a successful SSH login is a kill chain)

## Active response - automated containment

**Finding ID:** `DEF-004` | **Severity:** `High` (automated response that contains the attacker in seconds, without human intervention)

### Operational context

Active Response links a rule to a script executed automatically on the agent (or on the Manager) when the rule triggers. The classic use case is the firewall block of an IP that has exceeded a failed-login threshold: the same brute force detection seen in the SIEM (`../../../01-siem-log-analysis/elk-stack/`, DEF-001), but with automatic containment instead of just notification.

### PoC - Active response configuration (firewall-drop)

```XML
<!-- /var/ossec/etc/ossec.conf on the Manager -->
<active-response>
  <command>firewall-drop</command>
  <location>local</location>
  <rules_id>5763</rules_id>        <!-- rule: SSH brute force (multiple failed attempts) -->
  <timeout>600</timeout>           <!-- block the IP for 600 seconds -->
</active-response>
```

### PoC - automatic blocking in action

```
# [Attack] SSH brute force from IP 10.0.2.15 -> exceeds the threshold of rule 5763
** Alert: Rule 5763 (level 10) -> 'sshd: brute force trying to get access'

# Active Response executed automatically:
active-response/bin/firewall-drop: Adding IP 10.0.2.15 to iptables DROP   <-- IP blocked (DEF-004)
```

```Bash
# Verification on the agent: the attacker's IP is now blocked
iptables -L INPUT -n | grep 10.0.2.15
```

```
DROP   all  --  10.0.2.15    0.0.0.0/0        <-- attacker contained automatically
```

After the `timeout` (600 seconds), Wazuh automatically removes the rule, avoiding a false positive permanently blocking a legitimate IP.

### Tuning and defensive operations

- **Timeout and non-permanence:** prefer timed blocks to contain the impact of false positives; a permanent block should be reserved for high-confidence IOCs
- **Whitelist:** whitelist the management IPs and bastion hosts, to avoid self-blocking (a classic mistake is blocking your own administration IP)
- **Graduated escalation:** different actions for different severities (log, temporary block, host isolation)
- **Auditing:** every active response must be logged and reviewed; automation without review can be exploited by an attacker to cause a self-DoS (inducing the blocking of legitimate IPs)

## Lab experience

FIM gave the most immediate defensive satisfaction of the whole module. I had documented the persistence techniques in `07-post-exploitation` (addition of SSH keys, modification of system files); seeing them detected in real time by Wazuh - the `authorized_keys modified` alert appearing in the Dashboard at the very moment I simulated the backdoor - closed the loop between attack and defense. The same action that as an attacker guaranteed me access, as a defender betrayed me instantly.

Active Response was the most delicate part to tune. The first test worked too well: during a configuration test I self-blocked my administration IP, losing SSH access to the agent for 600 seconds. This "painful lesson" made concrete the principle that defensive automation is powerful but double-edged: a mistuned rule can turn into a self-DoS. The whitelist of management IPs, which initially seemed a detail, proved essential.

The operational reflection was on the trade-off between speed and risk. Active response reduces the containment time from minutes/hours (human intervention) to seconds (automation), but it transfers the risk: an automated false positive causes immediate damage. The timed timeout and the whitelist are the two controls that make this trade-off acceptable, containing the impact of an error.

## Theoretical analysis: detection without response is only half the defense

The XDR (Extended Detection and Response) model unites two functions that were historically separate: detecting and reacting. A classic IDS detects and notifies, leaving the response to the human operator; this introduces a time window - the "dwell time" between detection and containment - during which the attacker continues undisturbed. Much of the damage is done in that window: escalation, lateral movement, exfiltration.

Active response compresses this window to zero for known and high-confidence threats. It does not replace the analyst (complex decisions remain human), but automates the deterministic responses: if an IP does brute force, blocking it does not require judgment, it requires speed. Delegating the obvious decisions to automation frees the analyst for those that require context.

The mirror risk is that automation, devoid of judgment, also executes errors at the same speed. A false positive that in a manual system would be filtered by the analyst, in an automatic system becomes an immediate action (blocking a legitimate IP, isolating a production host). This defines the design principle of active response: automate only the responses to high-confidence detections, with safety controls (timeout, whitelist) that limit the damage of an error. Active defense is powerful exactly to the extent that its configuration is disciplined.

## Real-World scenario: detection and response in action

> This section describes how these defensive controls would operate in a real incident.

### Attacker perspective (what they attempt)

The attacker, having gained initial access, tries to establish persistence by adding an SSH key and then to expand with a brute force toward other internal hosts. They trust that the file modifications go unnoticed and that the brute force, if slow enough, does not exceed the thresholds.

### Defender perspective (how the controls respond)

```
[DEF-003] FIM detects the modification of /root/.ssh/authorized_keys in real time
        |
        v
Immediate alert: persistence attempted on host X
        |
        v
[DEF-004] The brute force toward internal hosts exceeds rule 5763
        |
        v
Active Response: attacker's IP blocked in iptables in <1s, 600s timeout
        |
        v
SOC: correlation of FIM + brute force -> host X compromised, containment and remediation
```

**Defensive value:** FIM betrays the persistence at the moment it is established, denying the attacker the advantage of silent permanence. Active response contains the expansion before it succeeds, reducing the dwell time to seconds. Together, detection and response break the kill chain at two points: persistence and lateral movement.

**Monitored indicators (IOC):** modifications to authentication files/system binaries (rule 550), brute force (rule 5763), rootcheck alerts, FIM + access sequences correlated in the SIEM.

**Defensive lesson:** detecting is not enough if the response is slow. The attacker operates at machine speed; a defense that responds at human speed gives them the window they need. Active response, tuned with discipline, brings the defense back to the same speed as the attack.
